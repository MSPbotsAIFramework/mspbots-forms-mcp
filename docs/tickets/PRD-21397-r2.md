### COV1 — imported title doesn't stick (regression: TC13)

QA-NIGHT: *"The tool reports '\<name\> (imported)' but the stored title equals the source's: the PATCHed source definition's title overrides the outer title."*

Confirmed by reading `src/mspbots_forms_mcp/tools/transfer.py:96-137`: `mspbots_forms_form_import` builds `patch_body["title"] = new_title` (the suffixed title) correctly, but `patch_body["definition"] = stripped_definition` is the deep-copied *source* definition with only `choicesByUrl`/`choicesSource`/tenant-key stripping applied (`_transfer_sanitize.py`'s `strip_tenant_specific` never touches a `title` key) — so if the source definition itself carries a top-level `"title"` (a standard SurveyJS root-level property, used by the builder/renderer as the form's own display title, independent of the wrapping form record's `"title"` field), that nested, unchanged, original title travels into the same PATCH call alongside the new outer `"title"`. `forms.py`'s own `mspbots_forms_form_update` docstring already flagged this exact ambiguity before this ticket existed (`forms.py:267-271`: *"Mutually exclusive with questions/pages in practice — the API contract doesn't specify what happens if \[title and\] definition \[are\] given together, so avoid combining them"*) — `transfer.py`'s import tool combines them anyway, and QA-NIGHT's live INT test is the first place that ambiguity resolved in the backend's favor of the nested `definition.title`.

Round 1's own regression test (`tests/test_transfer.py::test_export_then_import_roundtrip_is_field_for_field_identical`) didn't catch this because (a) its `SOURCE_FORM` fixture's `definition` has no top-level `"title"` key at all (only `"pages"`), so the collision this bug depends on never arises in the fixture, and (b) the test's only title assertion (`import_payload["title"] == "PRECICOM offboarding (imported)"`, line 328) checks the *tool's own echoed return value*, which `transfer.py` always sets correctly — it never checks what ends up inside `patch_call[2]["definition"]`, which is where the bug actually lives. This is exactly the "AC was meant to cover this, but no test case exercised the path" category of implementation error: round 1's own fixture happened to omit the one field that exposes the bug.

No AC in round 1 (AC1–AC8) literally states the new-form-naming requirement as a numbered acceptance criterion — it's stated only in Goals ("creating a new unpublished form with a new ID, named `'{original title} (imported)'`") and the Tech design's own example output, never promoted to a numbered AC. Formalizing it now (same requirement, just giving it a number so TC13 has something to cite):

- **AC9** (naming, added in this rework — not a new requirement, Goals/Scope item 2 restated as a numbered AC): Given F is exported and imported, Then the stored/effective title of the new form — what a subsequent `mspbots_forms_form_get`/`form_list` call on the new `form_id` actually returns, not merely what `mspbots_forms_form_import`'s own response says — equals the source form's title with `title_suffix` appended.

TC13 (new, dw: DW1 — the closest Done-when bucket; DW1 is the overall "is the created copy correct" criterion, and a title that silently reverts to the source's is exactly the kind of drift DW1 exists to catch, even though DW1's literal text is about field *definitions*, not the form-record title) asserts the PATCH body's `definition["title"]` is also overridden to the new title, using a fixture whose definition carries a top-level `"title"` key (the real-world shape round 1's fixture omitted).

### COV2 — choicesSource data-source questions that aren't tenant-key-shaped still leak through (regression: TC14)

QA-NIGHT: *"Forms uses choicesSource (mcp / api); the code only handles SurveyJS choicesByUrl (what TC4 tests). Imported data-source questions stay bound, the report is empty, and the MCP source parameters are silently dropped."*

Confirmed by reading `_transfer_sanitize.py:139-166` (`_walk`): a `choicesSource` dict is only acted on when `normalize_choice_source` exposes an `items` list *and* at least one item matches `TENANT_SCOPED_CHOICE_KEYS`. That conditional design came directly out of round 2's own review (`PRD-21397-review.md:50-51`, must-fix #1, itself built on sibling ticket PRD-21379's live-tested `choicesSource.items`/`attrs` shape for the Ginko `client_org` question) — it closed the *tenant-identifier-leak* case correctly, but it only ever covered the one real shape anyone had evidence for at the time (a cached, static `items` list). QA-NIGHT's finding is that `choicesSource` is also the wire shape for a genuinely live/external binding ("mcp / api") that carries its own source parameters and is not reducible to "does any item carry `tenantId`/`haloClientId`/`rewstOrgId`" — a `choicesSource` with no such key today still means the question's choices are not portable, static data: by construction, anything using `choicesSource` instead of a plain `choices` list is sourced from somewhere outside the static definition, and that is precisely what AC4/Done-when 4 ("fields bound to a data source... show as unbound and appear in the report") already says must be unbound and flagged — round 1/2's code just narrowed "data source" down to "choicesByUrl, or choicesSource-with-a-tenant-key-match," which is an under-approximation QA-NIGHT's real INT form exposed.

Neither `docs/` (`wiki find choicesSource` / `wiki find "data source dropdown"` / `wiki find "forms data source mcp"` — all three: no hits, 2026-11-10 sync, product version v20261104.1029) nor this repo's own code has the exact field names for the "mcp/api" `choicesSource` variant QA-NIGHT saw live on INT (QA-NIGHT's comment doesn't include a JSON sample either). Rather than guess field names for a shape no one here has seen, the safer and simpler fix — consistent with the ticket's own stated philosophy, "flag, not silently copy, anything that is tenant-specific" — is to drop the conditional entirely: **any `choicesSource`-shaped question is treated as data-source-bound by default** (stripped + reported, same unconditional treatment `choicesByUrl` already gets), not just the subset whose cached items happen to carry a tenant-scoped key. This also closes the "mcp/api" gap without needing to know its exact shape, at the cost of also flagging a `choicesSource`-shaped question that happens to hold only ordinary, ownership-free static options (e.g. a hardcoded Low/High priority list) — an over-flag, not an under-flag, which is the safe direction to err in for this ticket.

This supersedes the premise of the existing (round-2-added, not an `.ac.json`-governed case) test `tests/test_transfer.py::test_choices_source_shaped_ordinary_choices_are_not_over_stripped`, which currently asserts the opposite — that a `choicesSource` question with no tenant-key match must be left completely untouched. That test isn't one of this ticket's governed `.ac.json` cases (it was an uncredited extra the round-2 dev tick added alongside TC11), so revising or removing it is part of implementing this fix, not a change to a protected test case.

TC14 (new, dw: DW4 — exact fit, this is Done-when 4 itself) covers the broadened default.

### COV3 — workspace-admins-only is still not enforced anywhere verifiable (no code change; reaffirming round 1's assumption)

QA-NIGHT: *"The design says it is not done; neither the code nor the Forms API checks the role (judged from code)."*

This is accurate, and it's exactly what round 1 already said, explicitly, three review rounds ago (`PRD-21397.md`'s Open questions: *"'Workspace admins only' ... cannot be enforced inside this MCP server — it has no caller-role information, only tenant + a bearer credential ... This design does not add an in-server role check. If platform-side enforcement doesn't exist yet, that's a platform-team follow-up, not a blocker for shipping these two tools"*). Re-reading `server.py:61-96` at the current `main@62e4dc0`: still only `X-API-Key`/`X-MSP-Host`/`X-MSP-Tenant-Id`, still no caller-role signal of any kind — nothing has changed since round 1, and nothing in this repo *can* change it: there is no header, token claim, or API call available to this MCP server that identifies the caller's role within a tenant. Re-reading `README.md`'s "MSPbots Connector" section (`reference/readme-connector-section.md`, byte-identical here per round-1's own Self-test) confirms the mechanism round 1 assumed genuinely exists fleet-wide: *"Controlled: Role-based, per-tool allowlist. Deny by default."* / *"Set access. Create roles and decide which tools each role may call."* / *"owner / admin / member roles."* This is a **per-workspace, self-service** feature of the Agent Platform connector layer — each workspace's own admin decides, in the platform's own admin UI, which role may call `mspbots_forms_form_export`/`mspbots_forms_form_import` (or any other tool, for any connector). There is no registration-time or code-level default this MCP repo can set on a customer's behalf (`mcppub register`'s `credential_fields` cover connector credentials, not per-tool role scoping — confirmed by reading its `--help`), and no gateway change would add one either (this is an existing, working platform capability, not a missing one).

So this repo adds no code for COV3, same as round 1. What's different from round 1 is that it's now been tested and failed against a real tenant, meaning **either** (a) the test tenant's workspace admin simply never configured the allowlist restriction for these two tools (an operational gap, not a code gap — the capability to do so already exists), **or** (b) product/QA actually wants a *default*, out-of-the-box restriction that doesn't depend on each customer configuring it themselves — which this MCP server architecturally cannot provide (no role signal reaches it) and would need a new contract from the Agent Platform/gateway side, i.e. `references/mcp-track.md` §2.3 "network and control-plane changes go to Leo" territory, not something this ticket's track can decide or implement unilaterally.

Not re-opening as `[NEEDS PRODUCT]` this round: this exact ambiguity was already surfaced, explicit, and accepted through three review rounds without objection, and re-confirming it costs nothing the other three fixes depend on (COV1/COV2/FIND1 are unrelated to how COV3 eventually gets resolved). But it is flagged here plainly for whoever reads the next QA-NIGHT result: if COV3 fails again after this rework ships, that is re-testing something this repo was never designed to satisfy, and the real question for Micus/product is (a) vs. (b) above — not a code review finding on this repo. No regression test case is added for COV3 (it isn't one of the five numbered Done-when items either — Micus's decision (b) is a Scope/Decisions-section commitment, distinct from Done-when 1–5 — so `dw`-tagging and the "every Done when needs a case" rule don't require one, and there is nothing in-repo to assert against).

### FIND1 — forms over ~20k characters silently export empty (regressions: TC15, TC16)

QA-NIGHT: *"Forms over ~20k characters... export as only `omitted_fields:[\"form\"]`; importing that file succeeds silently and creates an empty 'Untitled form'. ... Export uses the generic output helper with a 20k cap."*

Confirmed by reading `_json.py:17` (`MAX_CHARS = 20_000`) and `transfer.py:62-68` (`mspbots_forms_form_export` serializes its whole envelope through `dump_json_capped` with no override). `dump_json_capped`'s truncation strategy (`_json.py:28-45`) only knows how to shrink a *list*-shaped field gracefully (`_truncate_list`/the list-key branch); the export envelope's `"form"` value is a *dict*, so an oversized form falls into `_shed_largest_values` (`_json.py:71-97`), which sheds whole top-level keys largest-first until the rest fits — for this envelope, that is the entire `"form"` key, leaving `{"export_version":1,"source_form_id":...,"truncated":true,"omitted_fields":["form"]}`. `mspbots_forms_form_import` (`transfer.py:108-110`) then does `form = export_payload.get("form") or {}` with no check that `"form"` is actually present and complete, so it proceeds to create a form from an empty dict — `title = form.get("title") or "Untitled form"`, an empty `definition`, no error, no refusal. The ticket's own named target form (Ginko's, ~62KB per QA-NIGHT) is squarely in the size range this breaks.

This directly breaks AC1 field-for-field fidelity for any form at or above the 20k-char budget — a real, not hypothetical, size class (QA-NIGHT's own 80-question/34KB test case, Ginko's 62KB form). `dump_json_capped`'s token-economy cap exists to keep *agent-facing* tool responses inside a context budget; `form_export`'s output is meant to be saved as a file and later fed back into `form_import`, not read by the calling agent as conversation context, so the budget that is right for every other tool in this server is the wrong default for this one. Two independent fixes:

- **Export** must not silently shed the form payload. Either export bypasses the capped helper for the `"form"` field entirely (returns the full, uncapped envelope — it's written to a file, not an LLM context window), or it refuses clearly when the full record won't fit rather than silently truncating. Round 1's own Tech design never called out `dump_json_capped`'s behavior on an oversized dict-shaped payload as a risk (it wasn't reachable with the hand-built fixtures round 1 tested against); this rework is where it surfaces.
- **Import** must not proceed on a `"form"` that is missing, empty, or carries `truncated`/`omitted_fields` — same "never half-import" principle AC6 already states for an unsupported `export_version`, extended to a structurally incomplete payload regardless of cause.

TC15 (new, dw: DW1 — exact fit, this is AC1's fidelity guarantee applied to the size class round 1's fixtures didn't cover) and TC16 (new, dw: DW1 — same AC1/fidelity bucket: a silent empty import is the sharpest possible fidelity failure) cover export and import sides respectively, both as pure-function/fake-client unit tests (a large synthetic definition fixture, no real tenant or INT needed).
